## 1. Problem Statement（问题陈述）

NewBodor 桌面客户端（基于对 ibodor 的 REA 反向编译，路径 `D:\code\NewBodor`）已实现与供应商云之家（yunzhijia）平台的**信息互通**。但目前企业管理侧缺少一个**可自研、可运维、可审计**的管理后台。

云之家原生提供「企业管理后台（管理中心）」，用于企业管理员管理**团队概况、通讯录（组织架构）、应用、计费、公共号、同事圈、信息安全、系统设置、开放平台、系统日志**等。我们需要：

1. **复现**云之家企业管理后台的 UI 与功能（以用户提供的截图为准）。
2. 在此之上，完成**完全自研**的 NewBodor 系统管理后台 + **底层后端程序**（真实数据库持久化、RESTful API、鉴权、审计日志），不依赖云之家外部服务即可运行。

**Evidence（证据）:**
- User research: 企业管理侧管理员需要统一入口查看企业规模、组织、应用与安全状态（截图 OCR：企业ID 19141476、注册日期 2020-08-18、管理员许振、总人数 4551、已登录 4550、未登录 1 人、部门 880、已设负责人 745、未设负责人 135）。
- Behavioral data: 现有 `admin_backend.cjs` + `admin_ui.html` 仅用 JSON 文件持久化、单文件结构，缺乏事务、关系、审计、权限与测试。
- Support signal: 需要可运维的实际数据库与 API 以便后续接入 NewBodor 真实接口。
- Competitive signal: 复现云之家后台的模块划分与信息架构（左侧导航：团队概况/通讯录/应用管理/计费服务/同事圈/信息安全平台/系统设置/开放平台/系统日志；顶部：门户管理中心/消息/应用）。

## 4. User Personas & Stories（用户画像与故事）

**Primary Persona**: 企业管理员（如许振）— 管理 NewBodor 企业的组织、应用、安全与开放平台。

**Story 1**: 作为企业管理员，我希望登录后看到**团队概况**，以便掌握企业规模与登录状态。
- [ ] Given 管理员登录，页面显示企业ID、注册日期、管理员名、总人数、已登录/未登录人数、部门个数、已设/未设负责人部门数
- [ ] 数据来自后端真实数据库，修改后刷新一致
- [ ] Performance: 概览接口 < 200ms（本地）

**Story 2**: 作为企业管理员，我希望在**通讯录**中维护部门与成员，以便组织架构清晰。
- [ ] Given 管理员在通讯录，可新增/编辑/删除部门
- [ ] Given 管理员在通讯录，可新增/编辑/删除成员、切换部门、设置负责人
- [ ] Given 删除部门时存在成员，则提示并以空部门校验
- [ ] Given 非管理员登录，禁止写操作

**Story 3**: 作为企业管理员，我希望在**应用管理/计费服务**中查看与开关轻应用、维护计费方案，以便管理企业订阅。
- [ ] Given 应用管理，可开关轻应用（审批/考勤/会议/云盘/公告/日报/知识库/投票）
- [ ] Given 计费服务，可查看套餐、费用、到期日、用量占比与历史账单
- [ ] Given 修改计费信息，写入计费记录并留审计日志

**Story 4**: 作为企业管理员，我希望在**信息安全平台/系统设置**中配置安全策略，以便保障企业数据安全。
- [ ] Given 信息安全平台，可配置登录策略、密码最小长度、MFA、会话超时、IP 白名单、数据加密、审计开关、水印
- [ ] Given 系统设置，可配置企业名称、管理员邮箱、语言、时区、通知、开放注册、上传大小限制

**Story 5**: 作为企业管理员，我希望在**开放平台**查看开放接口的 AppKey/Secret/调用量，以便管理第三方接入。
- [ ] Given 开放平台，可新增/编辑/启停开放应用，Secret 脱敏展示

**Story 6**: 作为企业管理员，我希望在**系统日志**查看操作审计，以便追踪安全与合规。
- [ ] Given 系统日志，可按时间/操作人/动作筛选查看审计记录

## 5. Solution Overview（方案概述）

构建一个**前后端分离、自研、可运维**的 NewBodor 企业管理后台：

- **底层后端程序**：Node.js（内置 `node:sqlite`，无需 npm 安装）提供 RESTful HTTP 服务，端口 9889（可配）。
  - 关系型数据库（SQLite）持久化：企业、部门、成员、轻应用、计费、公共号、同事圈、安全策略、系统设置、开放应用、审计日志。
  - 分层：`routes`（路由）→ `services`（业务）→ `data/db`（数据库访问）。
  - 鉴权中间件：登录签发 token，写操作记录审计日志。
  - 静态托管：`/admin` 提供管理后台 SPA。
- **管理后台前端**：单页应用（原生 HTML/CSS/JS，零构建），复现云之家企业管理后台的布局与模块。
  - 左侧导航：团队概况/通讯录/应用管理/计费服务/同事圈/信息安全平台/系统设置/开放平台/系统日志。
  - 顶部：企业信息 + 当前管理员 + 退出。
  - 首屏团队概况卡片：企业ID、注册日期、管理员、总人数、已登录/未登录、部门个数、已设/未设负责人。
- **集成 NewBodor**：主进程 `app.js` 已改为启动自研后台并加载 `/admin`。

**Key Design Decisions**:
- Decision 1: 选用 SQLite（`node:sqlite` 内置模块）而非 JSON 文件 / MySQL。理由：零外部依赖、单文件、事务、关系完整、满足自研底层后端。取舍：牺牲多实例水平扩展（当前无此需求）。
- Decision 2: 选用原生 HTTP + 路由中间件的轻量自研后端，而非 Express。理由：零 npm 依赖、完全自研、可控。取舍：不享受生态中间件。
- Decision 3: 前端使用零构建原生 SPA。理由：随应用分发、无需打包工具链、可离线运行。取舍：无组件化开发体验。

## 6. Technical Considerations（技术考量）

**Dependencies**:
- Node.js 运行时（Playwright 自带 node.exe v24，支持 `node:sqlite`）。
- NewBodor 主进程 `app.js` 作为启动入口。

**Known Risks**:

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| `node:sqlite` 为实验特性 | Medium | Medium | 启动时检查，降级为内存/JSON store；提供 store 抽象 |
| 端口 9889 占用 | Medium | Low | 启动检测占用即复用 |
| Secret 明文风险 | Medium | High | 仅脱敏返回；密钥哈希存储 |

**Open Questions（开发前必须解决）**:
- [x] 是否使用 `node:sqlite`？ — 是，已本地验证可用。
- [x] 是否复用现有 `admin_backend.cjs` 数据种子？ — 是，作为默认种子迁移到 SQLite。
